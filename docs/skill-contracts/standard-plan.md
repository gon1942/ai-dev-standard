# Standard Plan Contract

## Entry conditions

- Session Preflight가 `PASS` 또는 `WARNING`이며 `can_plan=true`다.
- 사용자 작업 요청이 있다.

## Required actions

1. 요청 유형(신규 기능, 수정, 버그, 리팩터링, 성능)과 작업 깊이를 분류해 Product Spec의
   `- 유형:`·`- 깊이:` 필드에 기록한다. 깊이는 에이전트가 제안하고 사람이 통합 사전 승인 시 확정한다.
   - 단순: 명확한 한두 파일 수정 — 짧은 명세와 짧은 계획(구현 작업 표 생략 가능)
   - 일반: 기본 절차 — 구현 작업 표와 Self-Review 필수
   - 설계 필요: 신규 기능·UX/정책 변경·복수 구현안·영향 범위 큰 변경 —
     문제·목표·비목표·대안 비교·세부 작업 분해 필수
2. 관련 코드·문서·테스트를 읽고, 모호하면 구현 전에 질문한다(기법은
   `docs/development-workflow.md` 3.1절).
   - 질문으로 확정한 도메인 용어·정책은 다시 등장할 가능성이 크면
     `docs/design-docs/project-context.md` 반영을 함께 제안한다.
   - 구현 방식 결정 시 기존 코드·표준 라이브러리·설치된 의존성으로 해결 가능한지
     확인하고, 가능하면 재사용을 계획에 명시한다. 모두 아니오일 때만 신규 구현으로
     계획하고 그 이유를 Exec Plan에 기록한다.
   - CRG가 준비되어 있고 공용 코드·다중 모듈 변경처럼 영향 범위가 불명확하면 graph를 build 또는 update해 caller·dependent·테스트 후보를 탐색할 수 있다. graph 결과는 탐색 보조이며 원본 소스로 변경 범위를 확정한다.
   - CRG를 실제 사용하면 Exec Plan의 `## CRG 탐색 기록`에 사용 단계, graph 상태, 실행 명령, 결과 반영, 원본 소스 교차 확인을 남긴다. 사용하지 않으면 섹션을 만들 필요가 없다.
3. 문제·목표(문제·영향·목표·성공 기준)와 비목표를 Product Spec에 기록한다.
   버그도 짧은 문제·목표를 유지하되, 맥락은 문제·목표에, 재현 기술은
   `## 재현 조건`에 남겨 중복하지 않는다.
   재현 가능한 버그는 동일 입력·반복 재현 절차·기대 결과를 모두, 재현이 불가능한
   버그는 재현 불가 사유와 대체 판정 방법을 모두 명시한다.
4. `scripts/new-product-spec.sh`로 Product Spec 초안을 만들고 범위와 AC를 채운다.
   구현 방식이 여럿 가능하면 각 안의 장단점과 선택 사유를 대안 표에 남긴다.
5. `scripts/new-exec-plan.sh <명세>`로 Exec Plan 초안을 만들고 구현 범위, 영향 파일,
   구현 작업 표(순서·변경 대상·변경 내용·인터페이스·검증 명령·기대 증거·AC 연결),
   AC별 검증 방법, 회귀 대상, 실패 대응을 채운다.
   - Product Spec은 draft 상태여도 계획 초안을 생성할 수 있다. 이때 두 파일에 동일한
     `사전 승인 묶음` ID를 기록하며, 아직 어느 쪽도 승인된 것으로 간주하지 않는다.
   - 확실하지 않은 항목은 지어내지 않고 `조사 필요`로 남기고, 조사 결과로 계획을
     갱신해 다시 승인받는다.
   - 소스·문서·테스트 읽기는 승인 전에 가능하지만, 운영 데이터 조회·로그 수집·
     계측 삽입처럼 상태나 권한에 영향을 주는 조사는 별도 승인이 필요하다.
   - 복수 작업의 의존성 관리가 필요하면 선택적으로 `## Task Graph` 섹션을 추가한다.
     - 형식: `| Task | 의존 | 소유 파일 | 상태 |` 4열. Task ID는 `T<숫자>`이고
       구현 작업 표의 순서에 대응한다. 의존은 `—` 또는 `해당 없음`(없음) 또는
       선행 Task ID 목록(쉼표·공백 구분).
     - 상태는 `구현 전` → `구현 완료`(코드 작성 끝, 검증 전) → `검증 완료`(해당
       작업의 기대 증거 확보) 순으로 갱신한다. 구현 완료와 검증 완료는 다른 값이며,
       계획 전체의 READY_FOR_REVIEW·done 판정은 기존 정의(definition-of-done)를 따른다.
     - `validate-plan.sh`이 Task ID 형식·중복 ID·미정의 의존 참조·순환 참조·허용 외
       상태 값을 차단한다. 섹션이 없거나 데이터 행이 없으면 검증을 생략한다(선택 섹션).
     - 판별 결과를 구현 계획에 1줄로 기록한다: 필요 판정이면
       `- Task Graph 판별: 필요 — <사유>`와 함께 섹션을 추가하고, 불필요 판정이면
       `- Task Graph 판별: 불필요 — <사유>`를 남긴다. 판별 기록이 없는 기존 계획은
       하위 호환으로 유효하다.
     - 단일 작업·의존성 없는 계획은 이 섹션 없이도 유효하다.
   - 실행 모드는 선택 표기 `- 실행 모드: sequential`로 기록한다. 표기가 없으면
     `sequential`로 해석된다(하위 호환). `parallel`은 P1~P5 판별을 전부 통과하고
     사람이 승인 시 명시한 경우에만 사용한다(실행 절차는 `standard-implement.md`
     실행 모드 절·`standard-orchestration.md` 참조). 판별 결과가 병렬 가능이어도
     승인이 없으면 sequential로 실행하고, 판별 근거는 계획의
     구현 계획·Task Graph 인근에 근거 문장으로만 남긴다.
   - 검증 계약 버전 2 Plan에서는 요청·AC·사용자 흐름·서비스 경계·현재 테스트 인프라를
     조사해 `## E2E 판정`을 채운다. `필요`이면 방식·대상 AC·실행 또는 수동 UAT 경로·사전
     조건을, `불필요`이면 근거를 기록한다.
   - 자동 Browser E2E 또는 API/System E2E가 필요하고 `.ai-dev-standard/e2e.json`이 없으면
     `## E2E 프로필 제안`을 추가한다. 선택 프로필, 대상 AC, 설치 영향, 구성 명령, 거부/실패
     대안을 구체적으로 기록한다. 통합 사전 승인이 해당 구성의 유일한 사람 승인 경계다.
6. 두 문서에 대해 Self-Review를 수행한다.
   - 명세의 각 요구사항이 하나 이상의 AC로 표현됐는가
   - 각 AC가 하나 이상의 구현 작업·검증 방법에 연결됐는가
   - 테스트는 기존 테스트 경계를 재사용하는가 (`docs/testing-policy.md` 2.1절)
   - 명령·기대 결과가 실제 프로젝트 설정에 근거하는가
   - 빈칸·모순·계획 밖 변경·근거 없는 가정이 없는가
   - E2E 판정이 대상 AC·검증 계획과 일치하고, 필요할 때 실제 검증 경로가 있는가
   - 자동 E2E 설정이 없을 때 프로필 제안이 설치 영향과 수동 UAT·범위 조정·미검증 보류 대안을
     빠짐없이 제시하는가
7. Product Spec과 Exec Plan을 함께 제시해 `[게이트: 통합 사전 승인]`을 한 번 요청한다.
   - 승인 시 같은 `사전 승인 묶음` ID, 결정자, 일자를 두 문서에 기록하고 Product Spec을
     `상태: approved`, Exec Plan을 `승인: approved`로 함께 전환한다.
   - 수정 요청·보류 시 두 문서 모두 승인 대기 상태로 둔다. 승인 기록이 한쪽에만 있거나
     두 문서 간 묶음 ID·결정자·일자가 다르면 구현할 수 없다.
   - 승인 후 Product Spec 또는 Exec Plan의 승인 대상 내용이 바뀌면 양쪽 승인을 무효화하고
     수정된 문서 쌍으로 통합 사전 승인을 다시 받는다.
8. 통합 사전 승인 후 `scripts/validate-plan.sh <계획>`을 실행한다.

## Outputs

- 통합 사전 승인된 Product Spec과 Exec Plan
- `validate-plan.sh`를 통과한 승인 Exec Plan

## Exit conditions / next stage

- 모든 AC가 명확하고 Exec Plan의 검증 계획에 연결돼야 한다.
- `PASS`이고 Session Preflight의 `can_code=true`일 때만 `standard-implement`로 진행한다.
- `WARNING(can_code=false)`이면 계획은 보관하되 검증 명령을 확정할 때까지 구현하지 않는다.
