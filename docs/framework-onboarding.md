# 프레임워크 온보딩

신규·기존 프로젝트에 공통 프레임워크를 처음 적용할 때의 안전한 절차다.

## 실행 시점

온보딩은 다음 경우에만 에이전트가 수행한다.

- 공통 프레임워크를 신규·기존 프로젝트에 처음 적용할 때
- 필수 파일·디렉터리 누락 또는 구조 손상을 발견했을 때
- 사용자가 프로젝트 재분석을 명시적으로 요청했을 때

일반 기능·버그·리팩터링 요청마다 온보딩과 전체 구조 검사를 반복하지 않는다. 이미 적용된
프레임워크에서는 제품 명세와 실행 계획 흐름으로 바로 시작한다.

프레임워크가 적용된 뒤의 일반 세션 시작 검사는 온보딩이 아니라 `docs/session-preflight.md`를 따른다.
같은 세션의 작업 요청마다 전체 검사를 반복하지 않는다.

## 온보딩 순서

1. 기존 프로젝트 적용 요청이면 먼저 `docs/framework-manifest.md`를 읽고
   `scripts/plan-framework-apply.sh --project-dir <대상>`으로 적용 분류 보고서를 만든다.
   이 보고서는 읽기 전용이며 생성·보존·병합 제안·제외를 구분한다.
2. `scripts/check-framework.sh`로 필수 골격을 확인한다.
3. 누락 또는 프로젝트별 설정 미확정이면 현재 작업 디렉터리에서
   `scripts/bootstrap-framework.sh --analyze`를 실행한다.
   이 명령은 읽기 전용이며 소스·문서를 수정하지 않는다.
4. 에이전트는 `scripts/analyze-project.sh --write`로
   `docs/generated/project-inventory.md`를 갱신한다. 이 파일은 소스 분석 사실만 담는 재생성 가능한 문서다.
5. 에이전트는 분석 결과로 사용자에게 다음을 제안·질문한다.
   - 프로젝트 목적과 주요 사용자 흐름
   - 언어·프레임워크·패키지 관리자
   - 실제 build/lint/test 명령
   - 외부 서비스·비밀값 처리 방식
   - 설계 문서와 브라우저·통합 검증 필요 여부
6. 사용자가 생성 범위를 승인하면 `scripts/bootstrap-framework.sh --init`을 실행한다.
   이 명령은 **없는 파일과 디렉터리만** 만들며, 기존 파일·소스 코드·의존성은 바꾸지 않는다.
7. 기존 파일의 내용 갱신, 검증 명령 연결, 의존성 설치는 제품 명세와 실행 계획을 만들어 별도로 승인받는다.

누락 골격 생성 뒤에는 `docs/project-bootstrap.md`에 따라 분석으로 알 수 없는 프로젝트 문맥만 질문하고,
답변을 근거로 아키텍처·프로젝트 문맥·프로젝트 원칙의 초안 또는 diff를 사용자에게 제안한다.

`--project-dir <프로젝트경로>`는 현재 작업 디렉터리가 아닌 다른 프로젝트를 검사·분석·초기화할 때만 사용한다.
외부 프로젝트의 기존 지침·설정은 자동 병합하지 않으며, `framework-manifest`의 승인 경계를 따른다.

## 신규 프로젝트

빈 저장소에서는 `--init`으로 문서·스크립트·디렉터리의 최소 골격을 만들 수 있다. 이후 에이전트가
사용자에게 프로젝트 목적, 주요 사용자 흐름, 기술 스택, 데이터·인증, 검증 방식을 질문한다. 답변을
바탕으로 `ARCHITECTURE.md`와 `docs/design-docs/project-context.md` 초안을 만들고, 실제 lint/test
명령 변경안을 제안한다. `.ai-dev-standard.env`는 처음에는 `template` 모드이며, 실제 lint/test 명령을
승인 후 연결한 뒤에만 `active`로 전환한다.

## 기존 프로젝트

`--analyze`는 `package.json`, `pyproject.toml`, `go.mod`, `Cargo.toml`, `Dockerfile`,
소스·테스트 디렉터리와 기존 지침 파일을 발견해 출력한다. 에이전트는 이를 근거로 유지·생성·갱신할
파일의 목록과 diff를 제안한다. `AGENTS.md`, `ARCHITECTURE.md`, `docs/design-docs/project-context.md`가
없으면 생성하고, 소스에서 확인 가능한 사실과 어긋난 프로젝트 구조 문서는 갱신안으로 제안한다.
기존 문서를 자동으로 대체하거나 코드에 손대지 않는다.

## 에이전트 실행 원칙

사용자는 온보딩 스크립트를 직접 실행할 필요가 없다. 해당 실행 시점에 에이전트가 스크립트를
도구로 호출하고 결과를 요약한다. 에이전트는 안전한 누락 골격과 재생성 가능한 분석 현황을 생성할
수 있으며, 기존 파일의 내용을 바꾸는 제안은 사용자 승인과 별도 제품 명세·실행 계획이 필요하다.

공통 정책, 보안 규칙, 완료 기준, 검증 정책은 소스 분석 결과만으로 자동 갱신하지 않는다. 이런 변경은
작업 완료 후 개선 후보로 제안하고 사람 승인 뒤 별도 개선 작업으로 진행한다.
