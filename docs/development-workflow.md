# 표준 개발 워크플로우 (도구 중립)

> 이 문서는 모든 AI 코딩 도구(OpenCode, Claude Code, 기타)와 모든 개발자에게
> 동일하게 적용되는 작업 흐름의 단일 진실 공급원(SSOT)이다.
> 각 도구의 스킬/에이전트는 이 문서를 따른다.

## 1. 핵심 원칙

1. **지침의 진실 공급원은 `docs/`** — AGENTS.md, CLAUDE.md, 각 도구 스킬은
   얇은 어댑터일 뿐 규칙을 복제하지 않는다.
2. **검증 진입점은 `scripts/verify-plan.sh <실행계획>` 하나** — 공통 검증
   (`verify.sh`: lint·typecheck·test)과 계획 검토를 함께 실행한다.
3. **AI의 완료 선언 ≠ 기능 완료** — AI는 `READY_FOR_REVIEW`까지만 선언한다.
   완료(`DONE`)는 검증 증거 + 사람 승인으로만 결정된다.
4. **제품 명세와 실행 계획은 1급 자산** — 모든 새 작업은 `docs/product-specs/`와
   `docs/exec-plans/`에 기록을 남긴다.
   기록이 없는 작업은 완료될 수 없다.
5. **실행 계층** — 프롬프트(지침) → 스크립트(검증). 스크립트 결과와 태스크
   기록이 완료 판정의 근거다.
6. **크로스플랫폼 진입점** — 모든 엔진 명령은 `node scripts/lib/cli.js <명령>`으로
   직접 실행할 수 있다. `scripts/*.sh`는 유닉스 환경용 얇은 shim이며
   `scripts/reference/`는 동치성 기준선 원본이다.

## 2. 표준 작업 흐름

```
기능 요청
   │
   ▼
① Session Preflight 상태 확인 — 세션 시작에 `scripts/session-preflight.sh --start`, 작업 요청에는 `--status`
   │       PASS·WARNING: Plan 가능 / Coding은 can_code 값(active 모드이고 BLOCK이 아님)으로 판정 / BLOCK·무효: 중단·재검사
   ▼
② 요구사항 분석 — 필요 시 그릴링 후 완료 조건(Acceptance Criteria) 표 작성
   │
   ▼
③ 제품 명세 생성 — scripts/new-product-spec.sh <작업명> <사용자 요청>
   │       질문·확정 요구사항·AC 작성 후 사람 승인(상태: approved)
   ▼
④ 실행 계획 생성·승인 — scripts/new-exec-plan.sh <제품명세파일>
       사람 승인(`- 승인: approved`) 뒤 `scripts/validate-plan.sh <실행계획파일>` 통과
   │
   ▼
⑤ 구현 — standard-implement 계약 따름
   │       (계획 범위 내 최소 diff, 기존 동작 유지)
   ▼
⑥ 검증 — standard-verify 계약과 `scripts/verify-plan.sh <실행계획파일>` 실행
        (공통 lint + typecheck + test 후, 플랜의 검증 계획·회귀 대상 확인.
         검증 방법이 UAT로 지정된 AC는 standard-uat 계약을 함께 수행)
   │       실패 시 수정 후 재실행 (원인 분석 없는 재시도 금지)
   ▼
⑦ 독립 리뷰 — standard-review 계약 또는 사람 리뷰
   │
   ▼
⑧ 최종 수렴 판정 — `scripts/converge-plan.sh <실행계획>`
       (AC PASS + 검증 증거 + 리뷰 PASS 확인, 실패 시 구현/검증으로 복귀)
   │
   ▼
⑨ 완료 기록 작성 — 실행 계획 파일에 완료 기록·AC 판정 추가
   │
   ▼
⑩ Pull Request — 실행 계획과 리뷰 결과를 함께 제출
   │
   ▼
⑪ 사람 승인 → 머지 → 실행 계획을 `completed/`로 이동
   │
   ▼
⑫ 선택적 회고 — 반복 문제는 `docs/agent-improvements/candidates/`에 후보로 기록
```

### 2.1 신규·기존 프로젝트 온보딩

에이전트는 공통 프레임워크를 처음 적용하거나 구조 이상·사용자 재분석 요청이 있을 때만
`scripts/check-framework.sh`를 실행한다. 누락 항목이 있으면 `scripts/bootstrap-framework.sh --analyze`로
프로젝트를 **읽기 전용** 분석한다. 기존 프로젝트 적용 요청은 그 전에
`docs/framework-manifest.md`와 `scripts/plan-framework-apply.sh --project-dir <대상>`으로
생성·보존·병합 제안·제외를 분류한다. 분석 결과를 사용자에게 제안하고 필요한 정보를 질문한 뒤,
승인된 경우에만 `--init`으로 누락 골격을 생성한다. 일반 기능 요청은 이 단계를 반복하지 않고
제품 명세부터 시작한다. 기존 문서·소스·의존성·검증 명령의 수정은 온보딩 자동 작업이 아니라
별도 제품 명세와 실행 계획으로 진행한다. 상세 절차는 `docs/framework-onboarding.md`를 따른다.
최초 적용 뒤에는 `docs/project-bootstrap.md`에 따라 프로젝트 문맥을 확정한다.

## 3. 요구사항 검증 (AC 정의)

### 3.1 모호한 요청은 먼저 질문한다

요청이 구현 범위·사용자 흐름·도메인 규칙·예외 처리 중 하나라도 모호하면,
AC를 작성하기 전에 담당자에게 질문해 결정을 기록한다. 이를 이 문서에서는
**그릴링**이라고 한다.

- 단순하고 영향 범위가 분명한 수정은 그릴링 없이 진행할 수 있다.
- 신규 기능, 정책/UX 변경, 여러 구현안이 가능한 변경, 영향 범위가 큰 변경은
  그릴링을 우선한다.
- 결정된 용어·제약·제외 범위는 제품 명세 또는 실행 계획에 남긴다.

그릴링은 질문 자체가 목적이 아니다. 구현과 검증 가능한 AC를 확정하는 것이 목적이다.

그릴링의 기법:

- 메시지마다 질문은 하나, 열린 질문으로 사용자가 묘사하게 한다. 선택지 제시는
  사용자가 막혔을 때만 쓴다 — 옵션은 답을 유도한다.
- 이해한 부분은 짧게(200~300단어) 되돌려 말하고(재구술), 추측은 추측으로 표시한 뒤
  "빠지거나 틀린 것이 있는가"를 묻는다.
- 필요하면 질문을 건너뛰고 바로 진행할 수 있음을 첫 메시지에서 안내한다.
- 작업이 커지는 것으로 판명되면 중단하고 깊이(4.1절)를 올려 다시 진행한다.

### 3.2 AC 작성

구현 시작 전에 완료 조건을 표로 정의한다. 정의되지 않은 요구사항은
구현할 수 없고, 검증할 수도 없다.

형식:

```markdown
| ID | 검증 항목 | 기대 결과 |
|---|---|---|
| AC-01 | 정상 시나리오 | ... |
| AC-02 | 예외 시나리오 | ... |
| AC-03 | 기존 기능 영향 없음 | ... |
```

각 AC는 가능하면 테스트와 연결한다 (`docs/testing-policy.md` 참조).

## 4. 작업 유형별 흐름

기본 흐름은 모든 작업에 적용한다. 아래 절차는 작업 유형에 맞게 추가한다.

### 4.1 작업 깊이

깊이는 `단순 / 일반 / 설계 필요` 3단계며, 에이전트가 제안하고 사람이 명세 승인 시 확정한다.

| 깊이 | 해당 작업 | Plan 산출물 |
|---|---|---|
| 단순 | 명확한 한두 파일 수정 | 짧은 명세 + 짧은 계획 (구현 작업 표 생략 가능) |
| 일반 | 기능 수정·버그·여러 모듈 변경 | 기본 절차 + 구현 작업 표 + Self-Review |
| 설계 필요 | 신규 기능·UX/정책·복수 구현안·영향 큼 | 문제·목표·비목표·대안 비교·세부 작업 분해 |

상세 규칙은 `docs/skill-contracts/standard-plan.md`를 따른다.

| 작업 유형 | 계획 | 구현 | 추가 검증 |
|---|---|---|---|
| 신규 기능/기능 개선 | 필요 시 그릴링, AC 정의 | 작은 단위 구현, 테스트 우선 | AC별 테스트·수동 증거, Spec Review |
| 버그 수정 | 재현 절차와 실패 조건 정의 | 원인 진단 후 최소 수정 | 재현 회귀 테스트, Spec Review |
| 리팩터링 | 변경하지 않을 동작과 경계 정의 | 외부 동작 불변 유지 | 기존 테스트·영향 범위 확인 |
| 성능 개선 | 기준값·측정 방법 정의 | 측정 가능한 변경 | 변경 전후 수치 비교 |
| 대규모/다중 작업 | 필요 시 별도 명세와 작업 의존성 작성 | 준비된 작업 단위부터 진행 | 통합 검증과 전체 AC 추적 |

## 5. 공식 작업 기록

새 작업은 사용자 요청을 `docs/product-specs/`에 먼저 기록한다. 명세가 `approved`가 된 뒤
`docs/exec-plans/active/`에 실행 계획을 만들고, 사람 승인·머지 후 `completed/`로 이동한다.
형식은 `docs/definition-of-done.md`의 스키마를 따른다.

제품 명세는 무엇을 만들지의 계약이고, 실행 계획은 어떻게 구현·검증할지의 계약이다.
구현자·검증자·리뷰어는 같은 두 경로를 지정해 작업한다.

- 명세 생성 시: 사용자 요청 원문·질문·AC 작성, 상태 `draft`
- 명세 승인 후: 실행 계획·검증 계획·회귀 검증 대상 작성, 상태 `active`
- 자동 검증 완료 시: 실행 계획에 완료 기록·AC 판정 추가, 상태 `READY_FOR_REVIEW`
- PR 승인·머지 후: 사람이 상태를 `done`으로 확정하고 `completed/`로 이동

AI 도구별 세션 파일(예: `.opencode/plan.md`)은 임시 작업용이며 팀 추적의 대상이 아니다.

## 6. 통제된 자기 개선

작업 완료 후 에이전트는 반복된 문제의 개선 후보를 기록할 수 있다. 후보는 사람 승인 전
공통 규칙·스킬·스크립트를 바꾸지 못한다. 승인된 후보도 별도 제품 명세와 실행 계획으로
구현한다. 상세 규칙은 `docs/agent-improvements/README.md`를 따른다.

## 7. 커밋 규칙

- 커밋 메시지: 프로젝트 컨벤션에 따름 (기본: `<type>: <요약>`)
- 하나의 커밋 = 하나의 논리적 변경
- 제품 명세와 실행 계획은 해당 작업의 코드와 함께 커밋한다
- AI 도구는 사용자 명시적 승인 없이 commit/push하지 않는다
- 커밋과 푸시는 별도 승인을 받는다 — 커밋 승인을 푸시 승인으로 재사용하지 않는다

## 8. 브랜치 규칙

- 공유 브랜치(예: `main`, `develop`)에 직접 커밋 금지
- 작업 단위 브랜치 권장: `feature/작업명`, `fix/작업명`
- 병합은 PR 경유 + 사람 승인

## 9. AI 도구 사용 규칙 (모든 도구 공통)

- 구현 전 `docs/development-workflow.md`(이 문서)와
  `docs/coding-standards.md`를 준수한다
- 요청 범위 밖 변경 금지 (발견하면 기록하고 별도 태스크로)
- 기존 기능 변경 시 사유를 완료 기록에 명시
- 실행하지 않은 테스트를 실행했다고 보고하지 않는다
- 검증 실패 시 원인 분석 후 수정 (억지 수정 금지)
- 민감정보(API key, 토큰, .env) 출력/커밋 금지
