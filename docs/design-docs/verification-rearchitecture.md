# 검증 계층 재구성 — 스킬 판단 + Node CLI 실행 + 사람 승인

- 상태: 제안 (비규범 — 개선 후보 승인 전까지 계약·스킬·게이트를 변경하지 않는다)
- 작성일: 2026-10-21
- 참조:
  - `docs/references/2026-10-20-competition-analysis.md` (경쟁 분석)
  - `docs/references/2026-10-21-verification-engine-research.md` (검증 엔진 조사)

## 1. 개선 목적

| # | 목적 | 현재 문제 |
|---|---|---|
| 1 | 크로스플랫폼 실행 환경 확보 | bash 전제가 "공통 프레임워크" 목적과 모순. Windows는 Git Bash/WSL 강요 |
| 2 | 검증 판단력 강화 | 스크립트는 "정해진 절차 실행"만 가능. "구현이 의도를 충족하는가"를 판단하는 절차가 계약에 빈약 |
| 3 | 자동테스트 불가 영역 검증 추가 | 화면 동작·API 흐름 등이 "수동 확인"으로만 처리, 재검증 루프 없음 |
| 4 | 리뷰 품질 향상 | 리뷰어 입력 미정의 — 세션 이력에 오염된 리뷰 위험 |
| 5 | 자기 보고 감소 | 에이전트가 "실행했다"고 기록한 증거 비중 — runner 직접 실행·수집으로 최소화 |

## 2. 책임 분리 모델 (4자)

```
스킬        무엇을 검증할지 판단 — AC 선별, UAT 필요 여부, 리뷰 방법 선택
Node runner 실제 명령 실행 → 출력·종료 코드 수집 (자기 보고 제거 지점)
Node gate   증거 형식·승인 상태·상태 전이 검사 (수렴, Implement 진입, done)
사람         승인과 done 확정
```

근거: Superpowers·OpenSpec 모두 Markdown이 실행 엔진을 없애지 않고 CLI를 유지한다.
"스킬이 Bash를 대체"가 아니라 "스킬 + Node CLI로 역할 분리"가 정확한 구조다.

## 3. 설계 원칙 (불변조건)

1. Implement 진입과 READY_FOR_REVIEW 전환은 **기계 게이트가 검사** — 스킬 지침으로만 대체하지 않는다
2. runner는 에이전트가 아닌 **명령이 직접** lint/test를 실행한다
3. `done`은 사람 승인 전 불가
4. 동치성 L1(종료 코드 + 판정 라인 바이트 일치) 미충족 시 bash를 제거하지 않는다
5. 증거의 공식 위치는 Exec Plan — 상태 파일은 재개 전용(휘발성)이다

## 4. 트랙 A — 스킬 계약 강화

### 4.1 standard-verify (수정)

- 5단계 절차 채택: IDENTIFY(증명 명령 결정) → RUN(실행) → READ(출력 전체·실패 수·종료코드 직접 해석) → VERIFY(증거가 주장을 뒷받침하는가) → CLAIM
- 판정 구조화: 3C 체크 (Completeness / Correctness / Coherence)
- **결정 사항**: 별도 standard-spec-verify 스킬은 만들지 않고 VERIFY 단계로 흡수.
  독립 시점의 일치 점검은 기존 Spec Review가 담당 — 자점검(verify) / 독립(review) 이원화.
  Spec 단계에서 변경 가능

### 4.2 standard-uat (신규, 선택 적용)

- 적용 조건: Plan 검증 계획표에서 해당 AC의 검증 방법이 "UAT"로 지정된 것만.
  전 작업 필수 게이트 아님
- 루프: 시나리오 추출 → UAT 실행 → PASS: 증거 기록 / FAIL: 원인 분석 → 수정 계획 → 수정 → 재검증
- **증거 위치 (핵심 결정)**:
  - 상태 파일(`<작업>-state.md`): 재개 체크포인트만 ("UAT 진행 중, 시나리오 2/4")
  - **최종 UAT 판정·증거는 반드시 Exec Plan 완료 기록·AC 판정에 기록** —
    converge-plan은 Exec Plan 파일을 직접 검사하므로, 상태 파일에만 있으면 수렴·리뷰 근거에서 누락된다

### 4.3 standard-review (보강 — 신규 작성 아님)

- 독립 리뷰어 분리는 기존 계약 유지
- 최소 입력 정의 추가: Product Spec + 변경 범위(diff) + 검증 증거. 구현 세션 이력 전달 금지
- 발견 분류: CRITICAL / WARNING / SUGGESTION

### 4.4 연동 파일

development-workflow.md(UAT 분기), definition-of-done.md(AC 판정 양식에 UAT 추가),
AGENTS.md/CLAUDE.md(문서 목록), .opencode·.claude 어댑터(참조),
new-exec-plan 골격(검증 방법 선택지에 UAT)

## 5. 트랙 B — Node CLI 이관 (6단계)

가치 순서와 구현 순서를 분리한다. 검증 엔진이 가장 중요한 자산이지만 가장 먼저 옮기지 않는다.

| 단계 | 내용 | 안전 장치 |
|---|---|---|
| 1 | Node 실행 기반 + 동치성 시험 체계 | 기존 bash 회귀 7종을 오라클로 사용 |
| 2 | 단순 생성 명령 이관 (new-product-spec 등) | 결정적 출력 — golden-master 비교 |
| 3 | lint/test 어댑터 이관 | Windows 경로·프로세스 실행 검증 |
| 4 | 핵심 게이트 이관 (validate·verify·converge) | L1 동치 없으면 bash 유지 |
| 5 | preflight·온보딩 이관 | — |
| 6 | 동치성 증거 확보 분만 bash 제거 | 스크립트 경로를 인터페이스로 유지하는 shim 전략 — 계약·스킬 무수정 |

### 동치성 정의

- L1 (계약): 종료 코드 + 판정 라인 바이트 일치 (PASS / FAIL / CONVERGENCE: PASS 등)
- L2 (참고): 타임스탬프·경로 정규화 후 전체 출력 일치

### 이관 범위

- 대상 20개: 배포 스크립트 (작업 흐름 9 + 온보딩 5 + preflight 3 + 개선루프 2 + 어댑터 1)
- 비대상 8개: 회귀 테스트 7종 + 템플릿 빌더 — 원본 저장소 전용, bash 영구 유지

### 트랙 병렬성

트랙 A(스킬)는 오늘의 bash 위에서도 유효하므로 트랙 B를 기다리지 않는다.
shim 전략으로 스크립트 경로가 인터페이스로 고정되어 양 트랙이 서로를 blocking하지 않는다.

## 6. 알려진 한계와 향후 옵션

- 로컬 runner·게이트는 자기 보고를 **크게 줄이지만 변조를 완전히 막지는 못한다**
- 변조 방지가 필요해지면 동일 Node gate를 CI 필수 검사로 실행 (현재 비목표, 별도 개선 후보로 승격)
- 도구별 서브에이전트 편차 (예: Codex 리뷰 에이전트 이슈) — "별도 에이전트·세션 또는 사람"
  우회 경로를 스킬마다 명시
- Node 없는 적용 프로젝트: AI 코딩 도구(OpenCode·Claude Code)가 이미 Node 기반 — 실질 부담 미미,
  문서로 명시

## 7. 프로세스 경계 (이 문서의 규범성)

- 이 문서와 참조 조사 2건은 **비규범**이다
- 실제 계약·스킬·게이트 변경은 다음 경로로만 진행한다:
  개선 후보 등록 (출처: 완료 작업의 실제 마찰 — 후보 3건은 독립 등록) → 사람 승인 →
  Product Spec → Exec Plan → 구현 → 검증
- 이 문서가 규범이 되는 시점은 개선 후보 승인 시점이다
