# 테스트 정책

> 검증의 구체적 기준. `scripts/test.sh`와 로컬 `scripts/verify.sh`가 이 정책을 실행한다.

## 0. 검증 활성화

템플릿 기본값은 `.ai-dev-standard.env`의 `template` 모드다. 이 상태의
`verify.sh` 결과는 템플릿 실행 확인일 뿐 완료 증거가 아니다. 프로젝트 적용 시
`active`로 전환하고 lint·test·필요한 typecheck를 필수 검사로 지정한다.
필수 검사가 실행되지 않으면 `verify.sh`는 실패해야 한다.

## 1. 테스트 계층

| 계층 | 목적 | 실행 시점 | 도구 예시 |
|---|---|---|---|
| Lint / TypeCheck | 문법·타입·스타일 위반 | 구현 완료 후 | ESLint, tsc, ruff |
| Unit Test | 개별 함수/모듈 동작 | 구현 완료 후 | Jest, pytest |
| Integration Test | 모듈 간 연동 | 필요 시 | Jest, pytest |
| Regression Test | 기존 기능 보호 | 구현 완료 후 전체 슈이트 | 전체 슈이트 |
| E2E | 사용자 시나리오 | 릴리스 전/필요시 | Playwright |

### 1.1 E2E 판정과 실행

- E2E는 웹 여부만으로 결정하지 않는다. 사용자 흐름, API/DB/외부 서비스 경계, CLI의 입력→결과
  흐름과 AC를 분석해 Plan에 `필요` 또는 `불필요`로 기록한다.
- Plan의 E2E 판정은 에이전트가 제안하고 사람이 Exec Plan 승인으로 확정한다.
- 자동 E2E는 `.ai-dev-standard/e2e.json`의 `command`와 `args` 문자열 배열만 사용하며,
  `node scripts/lib/cli.js test e2e`가 셸 없이 실행한다. Playwright는 선택 사항이다.
- E2E가 필요하면 `record-e2e-evidence`로 자동 실행 증거를 기록하거나 `standard-uat`의 수동
  UAT 증거를 남긴다. 설정 없음·실패·미실행은 PASS가 아니다.

## 2. 필수 규칙

1. **버그 수정은 재현 테스트부터** — 수정 전에 실패하는 테스트를 먼저 만든다
2. **기능 변경과 버그 수정은 테스트 우선 개발을 의무로 한다** — 상세 원칙은 §2.2를 따른다
3. **버그는 진단 후 수정** — 재현 → 최소화 → 원인 가설 → 필요한 계측/조사 → 최소 수정
   → 회귀 테스트 순서를 따른다. 원인 분석 없는 재시도는 금지한다.
4. **기존 테스트 삭제 금지** — 삭제가 필요하면 완료 기록에 사유 명시
5. **테스트를 통과시키기 위한 기능 축소 금지** — 근본 원인을 해결한다
6. **AC-테스트 연결** — 제품 명세의 AC 항목이 어느 테스트에
   대응하는지 가능하면 명시한다
7. **플랜 기반 검증** — 검증자는 실행 계획의 검증 계획과 회귀 검증 대상을 실행하고,
   결과를 같은 실행 계획의 AC 판정에 남긴다.

## 2.1 테스트 경계(seam)

- 검증은 가능한 한 **기존 테스트 경계를 재사용**하고, 새 경계가 필요하면 가장 높은
  지점에서 자른다(내부 구현이 아닌 공개 동작에서 테스트한다).
- 테스트 경계 수는 적을수록 좋다 — 이상적으로 하나.
- 실행 계획의 구현 작업 표와 검증 계획은 어느 경계에서 테스트하는지 명시하고,
  Plan Self-Review가 경계 재사용 여부를 점검한다.

## 2.2 테스트 우선 개발(TDD) 원칙

기능 변경 및 버그 수정은 테스트 우선 개발을 의무로 한다.

1. 자동화 가능한 신규·변경 동작은 해당 동작을 검증하는 테스트를 구현 전에 작성하고 실행하여,
   기대한 이유로 실패(RED)하는 것을 확인한다. RED 확인 시 실행 명령, 종료 코드, 실패 출력의
   핵심 내용 및 해당 AC를 Exec Plan 또는 완료 기록에 남긴다. 실패 출력에 비밀정보나 접속
   자격증명이 포함된 경우 기록 전에 제거한다.
2. RED는 기대 동작이 충족되지 않아 실패한 것이어야 한다. 종료 코드만으로 정상 RED로
   인정하지 않으며, 어떤 기대 동작이 미충족되어 실패했는지 식별할 수 있어야 한다.
   테스트 환경·설정·문법 오류는 정상적인 RED 증거로 인정하지 않는다.
3. 이후 최소 구현으로 테스트를 통과(GREEN)시키고, 필요한 리팩터링 후 관련 테스트의
   통과 상태를 유지한다.
4. 기존 구현이 요구사항을 이미 충족하는 경우에는 기존 테스트와 실행 증거로 충족 여부를
   확인한다. 추가 또는 변경이 필요한 동작에 대해서만 실패 테스트를 선행한다.
5. 자동화가 불가능한 AC는 사유와 수동 검증 절차(UAT 포함)를 실행 계획에 기록한다.
6. AC별 테스트와 검증 증거는 필수이며, TDD 수행 여부만으로 AC 충족을 선언할 수 없다.

## 3. 커버리지 기준

- 새로 작성/수정한 코드는 테스트 커버리지가 감소하지 않아야 한다
- 수치 목표(예: 80%)는 프로젝트 성격에 따라 README의 PLACEHOLDER에서 설정

## 4. 회귀 방침

- 구현 완료 시 기존 테스트 전체 실행 (`scripts/test.sh all`)
- 기존 테스트 실패가 기존 결함인 경우: 이번 변경과 무관함을
  입증(예: 변경 전에도 실패)하고 완료 기록에 기록한다
