# Definition of Done (완료 기준)

> AI의 구현 완료 선언과 프로젝트의 기능 완료 인정은 별개다.
> 이 문서가 정의하는 기준을 모두 충족해야 기능이 완료된다.

## 1. 완료 판정 상태

| 상태 | 의미 | 결정 주체 |
|---|---|---|
| `active` | 작업 진행 중 | — |
| `READY_FOR_REVIEW` | 구현+자동 검증 완료 | AI가 선언 가능 |
| `done` | 기능 완료 | **사람 승인만 가능** |

AI는 `READY_FOR_REVIEW`까지만 선언할 수 있다.
`READY_FOR_REVIEW`가 되려면 아래 2절의 자동 기준을,
`done`이 되려면 3절의 인간 기준까지 충족해야 한다.
사람 승인·개선 요청·보류의 선택과 기록은
`docs/skill-contracts/standard-human-decision.md`를 따른다.

## 2. 자동 완료 기준 (READY_FOR_REVIEW)

1. **요구사항 충족**: 제품 명세의 AC 표가 모두 충족됨
2. **검증 통과**: `node scripts/lib/cli.js record-verification-evidence <실행계획>` 종료코드 0
   (내부에서 공통 검증 `verify-plan`·`verify`를 직접 실행하고 실행 증거를 기록)
   (lint + typecheck + 테스트 전부)
3. **회귀 없음**: 기존 테스트가 새 변경으로 깨지지 않음
4. **기록 완료**: 실행 계획 파일에 완료 기록 섹션 작성됨
5. **범위 준수**: git diff가 계획 범위 내 (벗어난 변경은 완료 기록에 명시)
6. **수렴 판정**: `scripts/converge-plan.sh <실행계획>`이 통과
7. **E2E 판정 준수**: 검증 계약 버전 2 Plan에서 E2E가 `필요`이면 자동 E2E 또는 수동 UAT의 PASS 증거가 있다.

**AI가 작성한 PASS 보고 자체는 증거가 아니다.**
증거는 로컬 스크립트 실행 출력이며, 완료 기록에 명시된다.

## 3. 인간 완료 기준 (done)

1. 리뷰어(사람)가 완료 기록을 읽고 다음을 이해할 수 있음:
   - 무엇이 왜 변경되었는가
   - 무엇을 검증했고 무엇을 검증하지 못했는가
2. 리뷰 승인 + 머지

## 4. 제품 명세와 실행 계획 스키마

새 작업은 `docs/product-specs/`에 제품 명세 초안을 만들고, 이어서
`docs/exec-plans/active/`에 실행 계획 초안을 만든다. 두 문서를 함께 제시해 사람에게
통합 사전 승인을 한 번 요청한다.

제품 명세는 `scripts/new-product-spec.sh <작업명> <사용자 요청 원문>`으로, 실행 계획은
`scripts/new-exec-plan.sh <제품명세파일>`로 생성한다. draft 명세에서 생성된 계획은 두 문서에
동일한 `사전 승인 묶음` ID를 가진다. 한 번의 사람 승인 후 결정자·일자 및 승인 상태를 두 문서에
기록하고, `scripts/validate-plan.sh <실행계획>`을 통과해야 Implement에 진입할 수 있다.
기존 개별 승인 방식으로 이미 승인된 문서는 계속 유효하다. 리뷰 후 `done` 승인 절차는 별도다.

```markdown
# Product Spec: <작업명>

- 상태: draft
- 유형: 신규 기능  (신규 기능 | 수정 | 버그 | 리팩터링 | 성능)
- 깊이: 일반  (단순 | 일반 | 설계 필요)
- 사전 승인 묶음: PREAPPROVAL-YYYYMMDD-HHMMSS (Exec Plan 초안 생성 시 기록)
- 승인 결정자: <통합 사전 승인 후 기록>
- 승인 일자: <YYYY-MM-DD, 통합 사전 승인 후 기록>
- 사용자 요청: <원문>

## 문제·목표

- 문제: <현재 문제>
- 영향: <영향을 받는 사용자·기능>
- 목표: <이번 작업의 목표>
- 성공 기준: <사용자 관점의 성공 상태>

## 재현 조건 (유형이 버그인 경우만 작성, 다른 유형은 이 섹션을 지운다)

재현 가능하면 세 항목을 모두, 재현이 불가능하면 재현 불가 사유와 대체 판정 방법을
모두 채운다 (`scripts/validate-plan.sh`이 승인 후 이를 검사한다):

- 동일 입력: <조건>
- 반복 재현 절차: <절차>
- 기대 결과: <결과>

## 대안과 선택 사유 (구현 방식이 여럿 가능한 경우만 작성, 없으면 이 섹션을 지운다)

| 안 | 장점 | 단점 | 선택 여부·사유 |
|---|---|---|---|
| <안 1> | ... | ... | 선택 — <사유> |

## 확인 필요 사항

- ...

## 확정 요구사항

- ...

## 완료 조건 (Acceptance Criteria)

| ID | 검증 항목 | 기대 결과 |
|---|---|---|
| AC-01 | ... | ... |

## 범위

- 포함: ...
- 비목표(제외): 이번 작업에서 의도적으로 하지 않는 것: ...
```

```markdown
# Exec Plan: <작업명>

- 상태: active
- 승인: approved  (통합 사전 승인 후 기록)
- 검증 계약 버전: 2
- 제품 명세: docs/product-specs/<명세파일>.md

| 순서 | 변경 대상 | 변경 내용·인터페이스 | 테스트·검증 명령 | 기대 증거 | AC |

  - path/to/file.ext (+N/−M) — 변경 이유 한 줄
- 검증 증거:
  - verify-plan.sh 결과: PASS (verify.sh: lint 0 errors, tests 35/35)

- 커밋: <hash> | 미커밋(사유)
- 미검증 항목: <있으면 명시, 없으면 "없음">
```

## 5. AC 판정과 검증 증거

`READY_FOR_REVIEW` 및 `done` 기록에는 완료 기록과 함께 각 AC의 판정을 남긴다.
이는 Spec Review와 사람이 요구사항 충족 여부를 추적하는 근거다.

```markdown
## AC 판정

| AC | 판정 | 증거 |
|---|---|---|
| AC-01 | PASS | `tests/example.test.ts`의 테스트명 또는 수동 확인 결과 |
| AC-02 | PASS | UAT 시나리오 수행 절차와 관찰 결과 (standard-uat 계약) |
| AC-03 | 미검증 | 외부 시스템 접근 권한이 없어 PR 후 확인 필요 |
```

- 판정은 `PASS`, `FAIL`, `미검증` 중 하나다.
- `미검증`은 READY_FOR_REVIEW를 숨기기 위한 PASS가 아니며, 완료 기록의 미검증 항목에도
  구체적으로 반영한다.
- 실행 계획에서는 제품 명세의 각 AC가 검증 계획과 AC 판정에 각각 한 번씩 있어야 한다.

### 5.2 E2E 검증 증거

검증 계약 버전 2 Plan에서 `필요`로 승인된 E2E는 별도 증거를 남긴다.

- 자동 E2E: 프로젝트가 추적하는 `.ai-dev-standard/e2e.json`의 `command`와 `args` 배열을
  `node scripts/lib/cli.js test e2e`가 셸 없이 실행한다. `record-e2e-evidence`가 실제 명령,
  종료 코드, 안전한 결과 요약과 소스 상태를 `## E2E 검증 증거`에 기록한다.
- 수동 Browser UAT: 실제 시나리오를 수행한 뒤 같은 섹션에 `### 수동 UAT <식별자>`, 실행 일시,
  관찰 결과, `- 판정: PASS`를 기록한다.
- 설정 없음, 실행 실패, 브라우저·외부 환경 부재는 `미검증`이며 E2E 대상 AC를 PASS로 바꾸지
  않는다. `converge-plan`도 통과하지 않는다.
- 자동 Browser/API E2E에 설정이 없으면 승인된 Plan의 프로필 제안으로만 구성한다. 구성 명령은
  승인·프로필 일치를 확인하고 기존 유효 설정을 재사용한다. 설치 거부·실패는 수동 UAT, 범위 조정,
  미검증 보류 중 Plan에 적힌 대안을 따르며 PASS 증거가 아니다.
- E2E가 `불필요`이거나 버전 표기가 없는 레거시 Plan에는 E2E 실행을 추가로 강제하지 않는다.

### 5.1 자동 검증 증거

`node scripts/lib/cli.js record-verification-evidence <활성-실행계획>`은 검증 전의 Git 기반
소스 상태(계획 파일 자체 제외)를 수집하고 `verify-plan`을 직접 실행한다. PASS와 FAIL 모두
실행 계획의 `## 자동 검증 증거` 아래에 다음 기계적 사실만 추가한다.

- 실행 시각과 실제 실행 명령
- 종료 코드와 PASS/FAIL 요약
- Git HEAD 및 계획 파일을 제외한 작업 트리 식별자(또는 Git 미확인 사유)

전체 명령 출력, 환경 변수 값, 비밀값은 자동 기록하지 않는다. 이 명령은 **AC 판정, 리뷰 판정,
상태, 승인, `READY_FOR_REVIEW`, `done`을 변경하지 않는다.** AC의 의미적 충족 여부와 UAT
증거는 에이전트가 Verify 계약에 따라 별도로 기록하고, 사람 승인 경계도 그대로 유지한다.

기본 `verify-plan`과 `converge-plan`은 계속 읽기 전용이다. 자동 기록이 필요할 때만 전용
명령을 사용한다. `scripts/record-verification-evidence.sh`는 Unix 환경의 편의 shim이며,
Windows를 포함한 공통 진입점은 Node CLI다.

## 6. 미검증 항목의 의무 명시

검증하지 못한 것(브라우저 실측, 외부 연동, 성능 등)은
**"없음"으로 적지 말고 구체적으로 명시**한다.
숨겨진 미검증은 다음 담당자의 사고가 된다.

## 7. 최종 수렴 판정

`scripts/converge-plan.sh <docs/exec-plans/active/실행계획.md>`은 읽기 전용 최종 게이트다.
다음을 모두 확인할 수 있을 때만 `READY_FOR_REVIEW`을 허용한다.

- `.ai-dev-standard.env`가 `active` 모드
- 완료 기록 존재
- 모든 AC가 `PASS`이며 각 행에 비어 있지 않은 증거 존재
- 리뷰 결과가 `PASS`
- `verify-plan.sh`가 실제로 통과

`template` 모드, `WARN`/`FAIL`/`미검증` AC, 검증 실패는 수렴 실패다. 실패하면 구현·검증·리뷰 중
필요한 단계로 돌아가며, 수렴 스크립트가 실행 계획을 임의로 수정하지는 않는다.
